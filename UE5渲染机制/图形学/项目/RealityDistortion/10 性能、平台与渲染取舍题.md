# 10 性能、平台与渲染取舍题

> 这篇这次重写的重点，也不是“某个特性能不能开”，而是：
>
> **平台、性能和渲染特性的问题，重要的不是背答案，而是怎么组织决策数据。**

很多人答这类题时，容易一直说：

- `Nanite` 能不能用
- `Lumen` 能不能上
- `VSM` 能不能开
- 我会关掉这个、降掉那个

但面试官真正想听到的是：

**你怎么把平台、机型、帧率、资源和 fallback 组织成一套可上线的数据体系。**

---

## 一、这类题真正考的是什么

这类题表面上像是在问：

- `Nanite` 怎么上移动端
- `Lumen` 怎么上移动端
- 一个高配场景怎么降到手机
- GPU 爆了先砍什么

但底层其实是在问 4 件事：

### 1. 你会不会先问约束条件

比如：

- UE 版本
- 目标平台
- 目标机型
- 目标帧率
- 覆盖范围
- 是否允许高端特例方案

### 2. 你会不会做平台分级

不是一个开关决定全世界，而是：

- 高配一套
- 中配一套
- 低配一套

### 3. 你会不会组织特性开关和资源双轨

比如：

- 哪些资源要双轨
- 哪些材质要质量分级
- 哪些特性只能高端设备开
- 哪些必须有 fallback

### 4. 你会不会用数据而不是感觉做取舍

比如：

- GPU 时间预算
- CPU 时间预算
- 显存预算
- 包体预算
- 温控和掉帧风险

所以平台题成熟的答法，一定不是一句“能 / 不能”，而是：

**先问目标，再讲分级，再讲数据组织，再讲 fallback。**

---

## 二、答这类题时，最重要的“数据组织”要怎么讲

我最推荐直接把这类题拆成下面 5 层。

### 第 1 层：平台约束层

这层定义的是：

- 目标平台
- 目标 API
- 目标帧率
- 覆盖机型
- 发热与续航约束

### 数据通常放哪

- 平台规格表
- Device Tier 表
- 项目平台策略文档
- Data Table / 配置文件

### 第 2 层：特性策略层

这层回答：

- 哪些特性是默认主线
- 哪些特性是高端特例
- 哪些特性必须 fallback

典型内容包括：

- `Nanite` 是否允许
- `Lumen` 是否允许
- 阴影方案是哪套
- 反射方案是哪套
- 后处理质量档位

### 数据通常放哪

- `Device Profile`
- Scalability 配置
- Feature Policy Data Asset
- 平台条件开关表

### 第 3 层：资源轨道层

这层特别关键。

因为很多特性题如果只讲渲染开关，不讲资源组织，会很飘。

这一层回答的是：

- 是否需要高配 / 中配 / 低配资源轨
- Mesh 是否有 fallback
- 贴图是否分级
- 材质是否有简化版

### 第 4 层：运行时选择层

这层回答：

- 启动时怎么判设备档位
- 场景运行中怎么切策略
- 哪些参数是 profile 固定
- 哪些参数允许运行时动态降级

### 第 5 层：验证与回归层

这一层经常被漏掉，但真实项目里很关键。

这里要回答：

- 怎么证明这套方案真的稳
- 用什么数据做判断
- 回归关注哪些场景

典型数据包括：

- GPU 时间
- CPU 时间
- 内存 / 显存
- 实机温控
- 热点场景掉帧点

---

## 三、这类题最稳的统一回答模板

以后面试里，只要是平台和性能题，我最推荐按下面顺序答：

### 1. 先确认目标约束

先问：

- 平台
- 机型
- 帧率
- 覆盖范围

### 2. 再说特性是否能当默认方案

这一步要特别注意：

**“技术上存在支持”不等于“适合当项目默认方案”。**

### 3. 再说数据怎么组织

这一步最值钱：

- 设备分级表
- 特性策略表
- 资源双轨
- 运行时切换规则

### 4. 最后说 fallback 和验证方法

这样回答会特别像真实上线项目。

## 四、先记住 4 个基础口径

### 1. `Nanite` 不是通用移动渲染默认特性

按 UE5.7 官方 `Rendering Features for Mobile Games` 表，通用移动渲染路径里：

- `Nanite Virtualized Geometry` 不是默认移动特性

所以如果面试官问：

> “Nanite 怎么放到移动端？”

成熟的答法不是直接说“开”，而是先说：

**默认移动端主线方案不会依赖 Nanite。**

### 2. `VSM` 也不是通用移动默认方案

同一套官方移动特性表里：

- `Virtual Shadow Maps` 也不是默认移动方案

所以移动端 shadow 题，不能沿用桌面 `Nanite + VSM` 的默认前提。

### 3. `TSR` 也不是通用移动默认方案

UE5.7 官方移动特性表里：

- `TSR` 不是通用移动特性

所以移动端保画质问题，不能下意识先讲桌面上采样思路。

### 4. `Lumen` 的移动端要分“理论支持”和“项目默认方案”

UE5.7 官方文档里：

- 通用移动特性表不把 `Lumen GI and Reflections` 当默认移动方案
- 但技术细节文档又提到了特定 Android Vulkan 条件下的支持

这意味着你答题时不能一句话写死。

更成熟的答法是：

**Lumen 在 UE5.7 上已经出现特定移动平台口径，但它更像高端特例方案，而不是广覆盖移动项目的默认主线。**

## 五、实战题 1：`Nanite` 怎么放到移动端？

### 问题

如果一个高品质 UE5 场景依赖 `Nanite`，面试官问你怎么上移动端，你怎么答？

### 回答

我不会先答“直接开”或者“全部关掉”。

我会先说：

**先明确这是“广覆盖移动项目”，还是“高端机特例项目”。**

### 数据组织上我会怎么做

#### 1. 先做平台分级表

最少分成：

- `Tier_High`
- `Tier_Mid`
- `Tier_Low`

每档明确：

- 是否允许高端几何方案
- 目标分辨率
- 目标帧率
- 是否允许高成本阴影与反射

#### 2. 再做特性策略表

明确写：

- 高配是否允许 `Nanite` 路线
- 中低配是否强制 fallback mesh
- 哪些场景对象必须准备普通 LOD

#### 3. 再做资源双轨

这一层是最关键的。

我不会把问题理解成“移动端怎么硬开 Nanite”，而是：

**怎么让同一套内容同时具备高配路径和 fallback 路径。**

最常见组织方式是：

- 高配保留原高精资源
- 移动 fallback 使用普通 Static Mesh + LOD / HLOD
- 贴图和材质也做简化档位

#### 4. 运行时怎么切

- 用 `Device Profile`
- 用平台特性开关
- 用资源 cook / 打包策略

### 最成熟的一句

**移动端里的 Nanite 题，最重要的不是“能不能开”，而是“你有没有准备好一套不依赖它的主线资源组织方案”。**

## 六、实战题 2：`Lumen` 怎么上移动端？

### 问题

Lumen 很强，移动端怎么做？

### 回答

我会先说：

**要先区分“官方出现支持口径”和“适合当广覆盖默认方案”，这两件事不是一回事。**

### 数据组织上我会怎么做

#### 1. 先做光照策略分层表

我会直接定义：

- `LightingPolicy_High`
- `LightingPolicy_Mid`
- `LightingPolicy_Low`

比如：

- 高配：允许更动态的 GI / 更高质量反射
- 中配：受限动态光 + 低成本反射
- 低配：烘焙 GI + Capture + 最简动态补偿

#### 2. 再做平台绑定规则

- 哪些平台允许高端动态方案
- 哪些平台强制走 baked / simplified 路线
- 哪些设备必须锁帧保温控

#### 3. 再做材质与场景配套

如果高配和低配光照策略完全不同，材质本身也要配合：

- 反射依赖程度
- AO / cavity 的补偿程度
- 低配下是否要额外补假高光和间接光感

### 最成熟的一句

**Lumen 题最关键的不是“开不开”，而是先把“高配动态方案”和“广覆盖主线方案”拆成两张表。**

---

## 七、实战题 3：一个桌面高品质场景，怎么降到移动端

### 问题

一个 PC 场景要落移动端，你第一步怎么做？

### 回答

我不会先从某个材质节点开砍。

我会先把“要保住的内容”和“可替换的实现”分开，然后做一张降级矩阵。

### 我会怎么组织数据

#### 1. 先列视觉优先级表

比如：

- 绝对不能丢：主轮廓、主明暗关系、核心交互反馈
- 可以弱化：次级反射、微弱后处理、远景高频细节
- 可以替代：实时 GI、超高精几何、复杂透明层

#### 2. 再列系统级成本表

把成本按系统分类：

- 光照
- 阴影
- 几何
- 透明
- 后处理
- 材质
- 纹理

#### 3. 再形成替代表

例如：

- `Lumen -> baked GI / capture`
- `Nanite -> fallback mesh / HLOD`
- `VSM -> 更传统的移动阴影方案`
- `高频透明 -> masked / fake volume`

### 最成熟的一句

**降平台不是“哪里贵砍哪里”，而是先把“视觉目标”和“实现手段”分开，再替换实现。**

---

## 八、实战题 4：GPU 爆了先查什么

### 问题

场景 GPU 爆了，你怎么处理？

### 回答

我不会先靠感觉乱砍。

我会先组织一份 GPU 成本归因表。

### 我会怎么组织数据

#### 1. 先做 pass 级时间归因

比如按：

- BasePass
- Shadow
- Lighting
- PostProcess
- Translucency
- GI / Reflection

记录热点场景的 GPU 时间。

#### 2. 再做内容归因

例如：

- 哪几个灯最贵
- 哪几个特效最贵
- 哪类材质最贵
- 哪个区域 overdraw 最严重

#### 3. 再做降级策略表

对每类瓶颈给对应解法，而不是全场统一降。

### 最成熟的一句

**先做成本归因表，再做减法表，不要上来就无差别降质量。**

---

## 九、实战题 5：CPU 爆了怎么处理

### 问题

如果是 CPU 爆了，不是 GPU，你怎么做？

### 回答

这题最重要的是先把 CPU 成本也做成归因表，而不是继续盯着 shader。

### 我会怎么组织数据

#### 1. 系统分类

- Draw Call
- Tick
- 物理
- AI
- Niagara CPU Sim
- 动态生成 / 销毁
- Streaming / 加载

#### 2. 内容分类

- 哪类 Actor 太多
- 哪类组件太多
- 哪类系统持续 Tick
- 哪类对象最适合实例化

#### 3. 处理策略表

- 合批 / 实例化
- 关 Tick
- 中央化管理
- 减 spawn/destroy
- GPU 化粒子

### 最成熟的一句

**CPU 优化题如果还一直在谈 shader，通常就说明没有把成本归因分清。**

## 十、实战题 6：开放世界怎么控渲染成本

### 问题

开放世界可见范围大、内容量大，你怎么控成本？

### 回答

这题我会先讲可见性层级和资源层级，而不是某个单点特性。

### 我会怎么组织数据

#### 1. 可见性层级表

- 近景
- 中景
- 远景
- 超远景

每层定义：

- 是否保留完整材质
- 是否保留动态阴影
- 是否聚合成 HLOD
- 是否只保留大轮廓

#### 2. 资源组织表

- 英雄资源
- 常规资源
- 填充资源
- 超远景资源

#### 3. 流送与实例化策略

- 哪类必须实例化
- 哪类可延迟加载
- 哪类必须预留高精版本

### 最成熟的一句

**开放世界优化不是靠一个引擎特性解决，而是可见性、层级、实例化和流送一起做。**

---

## 十一、实战题 7：透明特别多，移动端卡，怎么做

### 问题

透明层很多，移动端 fillrate 爆了，怎么办？

### 回答

这题最重要的是先把它识别成：

**像素成本问题，而不是几何量问题。**

### 我会怎么组织数据

#### 1. 透明成本表

- 哪些透明材质覆盖最大
- 哪些粒子层数最多
- 哪些屏幕区域 overdraw 最高

#### 2. 透明分级规则

- 近景保留复杂透明
- 中景减少层数
- 远景改成 masked / flipbook / 简化面片

#### 3. 特效组织规则

- 雾层数限制
- 粒子叠层上限
- UI 与世界透明分开控预算

### 最成熟的一句

**透明题不该先从“模型多少面”开始答，而该先从“每个像素被画了几次”开始答。**

---

## 十二、实战题 8：如果要做高配 / 中配 / 低配三档，重要的数据怎么组织

### 问题

一个效果或场景要做三档分级，怎么组织才不乱？

### 回答

这题我会直接讲一套分级矩阵。

### 我会怎么组织数据

#### 1. 一张平台分级表

定义：

- `Tier_High`
- `Tier_Mid`
- `Tier_Low`

#### 2. 一张特性矩阵

列出：

- 几何方案
- 光照方案
- 阴影方案
- 反射方案
- 后处理方案
- 透明方案
- 材质复杂度方案

#### 3. 一张资源矩阵

列出：

- Mesh 轨道
- 材质轨道
- 贴图轨道
- 粒子轨道

#### 4. 一张运行时切换规则表

明确：

- 哪些启动时决定
- 哪些运行中可动态降级
- 哪些绝不能运行时切

### 最成熟的一句

**分级不是一个“全局质量值”，而是平台、特性、资源、运行时规则四张表。**

## 十三、如果面试官继续追问，我最该补什么

这类题继续往下追时，最值得主动补的是 3 件事。

### 1. 特性支持不等于项目主线

一定要主动说清：

- 理论可支持
- 但不一定适合作默认方案

### 2. 双轨资源组织

一定要主动说：

- 特性 fallback 不只是开关问题
- 很多时候是资源双轨问题

### 3. 验证方式

一定要补：

- profile
- 实机
- 温控
- 热点场景回归

因为没有验证方案的性能回答，会很像 PPT。

---

## 十四、这类题最容易踩的坑

### 1. 把“官方存在支持”答成“量产项目默认可用”

这是最大的坑之一。

### 2. 只会说开关，不会说资源组织

会显得只会背菜单，不会做项目。

### 3. 不问机型和帧率目标

没有约束条件，平台题答案会非常飘。

### 4. 只看 GPU，不看 CPU、内存和包体

真实项目几乎不会只受一个维度约束。

### 5. 只会砍成本，不会守视觉目标

真正成熟的降级，不是“什么都砍”，而是“保住最值钱的信息”。

### 6. 不讲 fallback

平台题最关键的往往就是 fallback 设计。

---

## 十五、结论

这类性能和平台题，真正想考的不是你背了多少 UE 特性，而是：

**你能不能把平台约束、特性策略、资源轨道、运行时切换和验证方法组织成一套完整的数据体系。**

只要这条线讲清楚，你的回答就会很像真实上线项目的人，而不是只会背“能不能开某个特性”的人。
