# 12 面试模拟追问 100 轮

> 这篇不是知识整理，而是口语训练稿。
>
> 用法最推荐这样：
>
> 1. 先只看问题，自己口头答一遍
> 2. 再看下面的参考答法
> 3. 把自己的答案压到 20-40 秒
> 4. 每次只练一组，不要一口气刷 100 轮

这篇故意写得更像面试现场，而不是文档说明。

## 一、项目定位与第一轮追问

### 1. 追问：你先不用讲细节，20 秒说清这个项目到底是什么。

**答：**

这是一个基于 UE5 渲染管线的空间裂隙系统，不只是做一个蓝色后效，而是让 receiver 在主视图、深度、阴影和 VSM 里都共同承认“这里被切开了”，最后再通过 `HoleInfo + Composite` 生成裂隙视觉。

### 2. 追问：为什么你一直强调它不是普通后处理？

**答：**

因为普通后处理主要改的是最终屏幕颜色，但我这个项目还改到了 `DepthOnly`、`BasePass`、`ShadowDepth` 和 VSM。也就是说，它不是只让画面看起来像裂开，而是让渲染系统真的接受这个洞。

### 3. 追问：如果我说这不就是“一个材质球特效”吗？

**答：**

如果只是材质球特效，就不需要改主视图深度和阴影链。我这套系统最难的地方，恰恰是让不透明 receiver 真的被裁掉，而不是在它前面再贴一层视觉。

### 4. 追问：你觉得这个项目里最有技术含量的地方是什么？

**答：**

最有技术含量的部分不是某个 shader，而是把 `field -> receiver -> SceneProxy -> MeshPass -> Depth/Base/Shadow/VSM -> Composite` 这条链真正接通，尤其是 shadow/VSM correctness 的收束。

### 5. 追问：那最有技术美术价值的地方是什么？

**答：**

技术美术价值主要在两块：一块是我把裂隙视觉拆成边界、pulse、折射、厚度和内部流动几层；另一块是 visualizer 球壳和参数控制链路，让它不只是一次性 demo，而是更像一个可调系统。

### 6. 追问：如果让我一句话理解你的职责，你会怎么说？

**答：**

我做的是从底层正确性到最终表现的整条链，不只是做出了效果，还把这个效果接进了 UE5 的主视图、阴影和 VSM 系统里。

### 7. 追问：如果面试官不懂 renderer，你怎么把这个项目说得不那么硬？

**答：**

我会先说它不是单纯贴一个视觉，而是“让物体真的在空间里被切开，并且阴影也跟着变”。先讲这个直观结果，再补是通过 renderer 链路做到的。

### 8. 追问：如果面试官很懂图形，你会怎么把高度抬上去？

**答：**

我会直接讲这是一个跨 `SceneProxy`、自定义 `MeshPass`、`Depth/Base/Shadow` 和 `VSM` 的系统接入，不是单个材质或单个 post effect。然后重点讲 `ShadowDepth + VSM cache/projection` 这块。

### 9. 追问：你这个项目现在最明确的未完成项是什么？

**答：**

最明确的是 `interior / cap pass`。现在洞已经成立，但切开后的内部表面还没有真正补出来，所以某些角度会有空壳感。

### 10. 追问：为什么你愿意主动讲未完成项？

**答：**

因为这反而说明我知道边界在哪里。真正成熟的表达不是假装全做完了，而是能清楚说出“主链已完成，下一步该补什么”。

### 11. 追问：这个项目如果让你自己打标签，你会打什么？

**答：**

我会打 3 个标签：`技术美术`、`渲染系统`、`阴影/VSM 正确性`。因为它同时跨了表现、引擎接入和底层验证。

### 12. 追问：你觉得这个项目更适合投 TA 还是引擎岗？

**答：**

两边都能讲，但讲法不同。投 TA 我会更强调视觉层次、参数化和工具化；投引擎我会更强调 `SceneProxy`、MeshPass、ShadowDepth 和 VSM 收束。

### 13. 追问：为什么你没有把它做成一个“纯展示型”特效？

**答：**

因为我想练的不是最后贴一个效果，而是让系统承认这个效果。这类项目的难点不是“好不好看”，而是“主视图、阴影和深度是不是统一”。

### 14. 追问：如果我问你这个项目最像哪一类问题，你会怎么归类？

**答：**

我会把它归成“自定义可见性 / 裁切 + 屏幕空间合成 + 阴影正确性”的复合问题，而不是单纯的材质表现问题。

### 15. 追问：你做完这个项目后最大的认知变化是什么？

**答：**

最大的变化是我不再只盯某个 shader 文件，而是会沿着 `组件 -> SceneProxy -> SceneVisibility -> MeshPass -> Shader -> Shadow/VSM` 整条链判断问题在哪一层。

## 二、渲染链路与场景代理追问

### 16. 追问：为什么要自定义 `UDistortionMeshComponent`？

**答：**

因为我需要从组件层就明确“谁是 receiver”，并切到自定义 `SceneProxy`。这一步还能顺带打标记、控制 shadow invalidation 语义，决定后面整条链能不能被接管。

### 17. 追问：你打 receiver 标记为什么用 `CustomPrimitiveData[0]`？

**答：**

因为它轻量、跨 pass 好读，而且不需要额外引入很重的结构。后面的 `DepthOnly`、`BasePass` 和 `ShadowDepth` 都能用这个标记快速判断当前 primitive 是否应该被裁切。

### 18. 追问：为什么还需要 `FDistortionSceneProxy`，只在组件里打标记不够吗？

**答：**

不够。标记只能告诉 shader“你是谁”，但 `SceneProxy` 决定的是“你到底被提交成什么 mesh、走什么路径、阴影拿到什么数据”。这层不接管，后面很多 pass 仍然可能走默认提交路径。

### 19. 追问：`GetDynamicMeshElements()` 现在在你的项目里还是主路径吗？

**答：**

不是了。旧阶段里它确实承担过 receiver 的动态收集和重组职责，但当前版本的常规渲染与阴影主路径已经回到静态提交结构。

现在更准确的说法是：

- receiver 的主收益来自静态 mesh command / 静态 shadow mesh
- `GetDynamicMeshElements()` 不再是这套系统的核心性能主线
- 真正按当帧 field 做动态粗筛的，主要是 `RealityDistortionPassProcessor::AddMeshBatch()`

### 20. 追问：那 `GetShadowMeshElement()` 又解决什么？

**答：**

它解决的是阴影收集路径。主视图和阴影不是同一批 draw command，所以如果只接管前者不接管后者，很容易出现“主视图对了，阴影还是走默认路径”的问题。

### 21. 追问：为什么现在 `DrawStaticElements()` 不能再置空？

**答：**

因为当前版本已经依赖它来保住静态 shadow mesh 注册和 VSM 缓存收益。

现在如果继续置空它，损失的不是“错误旧路径”，而是：

- 不相交 receiver 的静态缓存能力
- 正常的静态 shadow 提交收益

所以这条结论已经从旧阶段的技巧，变成当前版本里必须纠正的旧说法。

### 22. 追问：`GetViewRelevance()` 在这里怎么理解？

**答：**

它是在告诉 renderer 这个 primitive 该以什么姿态参与视图，比如：

- 是否沿用静态相关性
- 是否参与阴影
- 是否需要因为调试 cvar 暂时关闭某些相关性

当前版本里它更重要的意义，是：  
**receiver 已经不再默认伪装成动态物体，而是尽量沿用静态路径，只在需要的地方额外改 receiver 语义。**

### 23. 追问：为什么 `SceneVisibility` 也是你这个项目的关键点？

**答：**

因为 renderer 先得知道这个 primitive 要参加 `EMeshPass::RealityDistortion`，后面 `PassProcessor` 才有东西可处理。没有 `SceneVisibility` 这一站，自定义 pass 就只是代码存在，不会真的参与视图调度。

### 24. 追问：你怎么理解 `PassProcessor` 在这条链里的位置？

**答：**

我会把它理解成“把接管过的 mesh 真正编进 draw command 的那一站”。`SceneProxy` 决定谁来，`PassProcessor` 决定进来以后怎么筛、怎么选 shader、怎么组装渲染状态。

### 25. 追问：为什么 `AddMeshBatch()` 和 `TryAddMeshBatch()` 要分开？

**答：**

因为它们解决的粒度不同。`AddMeshBatch()` 更像“这批 mesh 是否有资格进这条 pass”，`TryAddMeshBatch()` 更像“当前材质和当前状态能不能正确参与构建”。分开之后逻辑更清晰，也更利于调试。

### 26. 追问：你的自定义 pass 当前真正写出的是什么？

**答：**

当前它写出的核心不是最终颜色，而是 `HoleInfoTexture`。更具体地说，当前最关键的有效数据是洞表面的 `DeviceZ`，它是后面屏幕空间重建的基础。

### 27. 追问：为什么你没有一开始就把很多材质信息写进 `HoleInfoTexture`？

**答：**

因为第一阶段我更关心 correctness 主链能不能先站住，所以先让它承担最核心的信息载体角色。等链路稳定之后，再考虑是否升级成多通道或增加辅助 RT 去承载更多材质语义。

### 28. 追问：你怎么理解 `DeferredShadingRenderer` 在你的项目里的角色？

**答：**

它一头负责调度 `RealityDistortion` 的 HoleInfo pass，一头负责调度最终 Composite。所以它是“从中间数据记录到最终屏幕合成”的总调度点。

### 29. 追问：为什么你把 Composite 放在 post-lighting 段？

**答：**

因为这一步更像是在已有主视图结果上做洞信息重建和风格化合成。它不是在替代 BasePass，而是在光照完成后，把洞表面信息和场景颜色再加工成最终裂隙视觉。

### 30. 追问：这条渲染链里如果只能让面试官记住一个图，你希望是哪张？

**答：**

我最希望他记住的是：`Field -> Receiver -> SceneProxy -> MeshPass -> HoleInfo -> Composite -> Depth/Base/Shadow/VSM`。因为这张图一旦记住，后面所有局部问题都能挂回这条主链上。

## 三、Shadow / VSM 与 correctness 追问

### 31. 追问：为什么主视图洞成立，不代表阴影一定对？

**答：**

因为相机看到的第一个表面，和光源看到的第一个挡光表面不是一回事。主视图洞成立只说明相机方向正确，不代表 `ShadowDepth` 和后面的 VSM 也接受了同一个洞。

### 32. 追问：`ShadowDepth` 在你这里的职责到底是什么？

**答：**

它负责让光源视角的挡光关系也承认这个洞。也就是从光源看过去，被 field 裁掉的 receiver 片元不再写入阴影深度。

### 33. 追问：为什么你说 `ShadowDepth` 对了也还不够？

**答：**

因为 VSM 不是到 `ShadowDepth` 就结束了。后面还有 cache、clipmap、projection 和最终 `ShadowMask`，它们都可能继续复用旧答案。

### 34. 追问：你怎么判断问题是在 `ShadowDepth`，还是在 VSM 后段？

**答：**

我会先看主视图 `SceneDepth`，再看 `ShadowDepth` 是否开始 clip。如果前两层都对，但最终阴影仍然不对，那问题大概率就在 VSM 后段的 cache、clipmap 或 projection。

### 35. 追问：你这次最关键的 VSM 经验是什么？

**答：**

最关键的是终于把“shader 没生效”和“缓存继续复用旧结果”区分开了。很多时候不是 clip 没执行，而是旧 cache 还在把你盖掉。

### 36. 追问：为什么现在不能只把 `ShadowCacheInvalidationBehavior = Always` 当成最终答案？

**答：**

因为当前真正成立的，已经不是“所有 receiver 无条件 Always”，而是：

- component 侧用 `Always` 作为进入检查集合的入场券
- proxy 侧再根据 field 相交关系动态返回 `Always` 或 `Static`

所以 `Always` 本身不是 hack，但现在它只是一半语义。  
完整答案已经变成：

**静态提交路径 + 条件式 invalidation。**

### 37. 追问：那它的代价是什么？

**答：**

代价仍然存在，只是已经比旧的全量 Always 收束很多。

当前代价主要是：

- receiver 仍然要进入每帧检查的集合
- proxy 仍然要做相交判断
- 如果灯光和阴影 view 很多，整体阴影成本依然会被放大

所以它是当前稳定正确的工程解，但不是“从此零成本”的银弹。

### 38. 追问：你怎么跟别人解释 `ShadowMaskTexture` 不是 shadow map 本体？

**答：**

我会说 `ShadowMaskTexture` 更像“最终屏幕这个像素受了多少阴影”，而不是“光源视角的深度图”。它是投影回主视图之后的结果，不是最前面的阴影输入数据本体。

### 39. 追问：为什么 `r.RealityDistortion.ShadowDepthClip` 一开始看起来像没生效？

**答：**

因为旧缓存还在，视觉上看不到差异。强制 invalidation 之后，0/1 的差异才会稳定出现。这类现象最容易让人误判成“代码完全没工作”。

### 40. 追问：如果有人说“既然这么麻烦，不如别动阴影了”，你怎么回？

**答：**

那就会退回到“主视图看起来像洞，地面阴影还是完整立方体”的假状态。这个项目最值钱的地方恰恰是没有停在视觉假象，而是把阴影 correctness 也做进去了。

### 41. 追问：VSM 这块如果让你再做一次，你会怎么安排顺序？

**答：**

我会更早把问题切成三层：`ShadowDepth`、cache/clipmap、projection。这样会更快定位是前段没承认这个洞，还是后段还在复用旧世界观。

### 42. 追问：为什么你说这个项目最强的不是“效果”，而是“correctness”？

**答：**

因为漂亮的视觉层谁都能往上加，但主视图、深度、阴影和 VSM 是否共同接受这个洞，决定了它到底是一个真正的系统，还是一个只在镜头前成立的假效果。

### 43. 追问：如果面试官追问“你怎么验证自己真的修对了”，你怎么答？

**答：**

我会说我不是只看最终画面，而是分层验证：主视图 `SceneDepth`、`ShadowDepth`、VSM 后段和最终 `ShadowMask` 都要能解释得通。只有层层对上了，我才会说这个问题是真的收束了。

### 44. 追问：如果要把你这次 shadow 经验抽象成一句方法论，你会怎么说？

**答：**

我会说：先切层，再看路径，再看输入输出，最后才判断逻辑。这个顺序比具体改了哪句代码更值钱。

### 45. 追问：现在 shadow/VSM 还有什么不是彻底完成态？

**答：**

底层 correctness 主链已经基本站住了，但如果继续做工程优化，还可以往更细粒度的 invalidation 和更清晰的调试视图继续推进。

## 四、Composite、材质与表现层追问

### 46. 追问：`RealityDistortionComposite.usf` 在你的项目里到底负责什么？

**答：**

它负责最终屏幕上裂隙视觉的成立，包括边界、pulse、折射、厚度吸收和 glow。前面的 `HoleInfo` 更像中间数据，真正“好不好看”是在 Composite 这里落地的。

### 47. 追问：为什么你一直强调 `SceneColorInputTexture` 不能替代挖洞？

**答：**

因为它只回答“洞里最终显示什么”，不回答“前面的不透明 receiver 是否真的不存在”。如果不先挖洞，后面采到的还是裁切前的结果。

### 48. 追问：你会怎么一句话解释这件事给不懂图形的人听？

**答：**

我会说：如果前面的墙还站着，你在后面贴一张“墙后面的风景”也没用，因为这堵墙本身并没有真的消失。

### 49. 追问：当前裂隙视觉你觉得最关键的 3 层是什么？

**答：**

我觉得最关键的是边界切口层、主/次 pulse 节奏层和折射/厚度吸收层。前者决定“是不是裂开了”，中间决定“是不是活的”，后者决定“是不是空间层而不是贴片”。

### 50. 追问：为什么你会把视觉拆这么细？

**答：**

因为只有拆开，才能知道是哪里不成立。比如“像贴片”通常是折射和厚度层不够，“像静态截面”通常是 pulse 层不够，“边界不锋利”通常是切口层的问题。

### 51. 追问：你现在最满意的一点视觉收束是什么？

**答：**

我比较满意的是边界主次关系终于站住了，不再是早期那种整面蓝底加一圈边，而是边界、内部、折射和 glow 开始形成清楚的层次分工。

### 52. 追问：你现在最不满意的一点是什么？

**答：**

还是内部成立性。现在有内部流动和空间感，但没有真正的切面和内壁，所以某些角度仍然会暴露“里面其实还是空的”。

### 53. 追问：如果让你继续 polish，你会先改哪？

**答：**

我会先继续围绕 `RealityDistortionComposite.usf` 收边界带、pulse 主次和 transmission 的平衡，而不是再往里面硬加更多元素。因为当前更需要收结构，不是堆特效。

### 54. 追问：如果让美术更好调这个效果，你会怎么做？

**答：**

我会把关键参数集中成更明确的参数块，比如边界、pulse、折射、内部层次分组，再配合更清楚的说明和预设，而不是让人直接去翻 shader 里的硬编码常量。

### 55. 追问：为什么你不直接让 receiver 材质去决定最终裂隙外观？

**答：**

因为当前主线里，最终裂隙外观依赖的是屏幕空间重建和合成逻辑，不只是某个表面材质。receiver 材质可以决定是否参与和某些基础通路，但最终大部分风格还是在 Composite 里统一控制更合理。

### 56. 追问：如果以后要让材质更深度参与最终风格，你会怎么升级？

**答：**

我会先升级 `HoleInfoTexture` 或增加辅助 RT，让它不只传 `DeviceZ`，还能传更多材质语义，比如颜色、mask 或别的风格参数。否则再复杂的 receiver 材质也很难真正进入最终合成。

### 57. 追问：为什么 visualizer 球壳不是主链的一部分？

**答：**

因为它的职责只是显示 field 的位置和范围，不负责 receiver 过滤、不写 `HoleInfo`、也不改 `Depth/Base/Shadow/VSM`。它更像一个显示层，而不是剔除逻辑本体。

### 58. 追问：为什么 visualizer 做成双层球壳？

**答：**

因为单层透明球壳很容易像一张玻璃片。双层结构可以用很低成本补一点内腔和厚度感，让它更像能量壳，而不是一张透明圆面。

### 59. 追问：为什么 visualizer 改成 opt-in 材质方案？

**答：**

因为旧方案自动分配和历史 managed 资产混在一起，长期维护会越来越乱。改成 opt-in 之后，资源生成、绑定和清理的边界都更清楚，也更像正式工作流。

### 60. 追问：visualizer 现在还有什么明显没补完？

**答：**

最明显的是时间和 pulse 现在还是静态输入，也就是材质图的动态能力已经留口了，但运行时还没真正把它驱起来。

## 五、数据组织与实战题追问

### 61. 追问：为什么你最近一直在强调“数据组织”？

**答：**

因为真实项目里，效果能不能做出来通常不是最难的，最难的是怎么让地表、道具、关卡和平台都能共享同一套逻辑，还能继续让美术调。只讲表现，不讲数据组织，最后很容易碎成一堆单点方案。

### 62. 追问：你说的“数据组织”最核心的两条链是什么？

**答：**

效果题我会用：`全局状态 -> 区域驱动 -> 场景采样 -> 资产响应 -> 人工修正`。平台题我会用：`平台约束 -> 特性策略 -> 资源轨道 -> 运行时切换 -> 验证回归`。

### 63. 追问：为什么效果题里你总把“全局状态”和“区域驱动”分开？

**答：**

因为它们职责不同。全局状态回答“世界现在处于什么阶段”，区域驱动回答“哪里受影响、影响多远、方向是什么”。这两层混在一起，系统很快就会变乱。

### 64. 追问：RVT 和 RT 你通常怎么选？

**答：**

大范围、长生命周期、很多资产都要稳定读取的场景数据，我更倾向 RVT。局部交互、短生命周期、频繁写入变化的东西，我更倾向 RT。

### 65. 追问：为什么你说“统一的是驱动，不统一的是响应”？

**答：**

因为世界里的变化通常是一份共享状态，比如水位、湿度、污染强度，但石头、木头、金属对这份状态的反应不一样。如果连驱动都各写各的，系统会碎；如果响应都强行统一，视觉又会假。

### 66. 追问：如果面试官问“河流干涸怎么做”，你最想先说哪句话？

**答：**

我会先说：这题我不会先把它理解成一个材质问题，而是先拆成全局水位、河道区域影响和历史水位残留这三层数据，再让地表和道具统一读取、分材质响应。

### 67. 追问：为什么你在河流题里特别强调“历史记忆层”？

**答：**

因为干涸不是把湿润值归零就结束了。合理的结果应该保留曾经有水的痕迹，比如水位线、泥痕、青苔残留。这些都是“当前状态”以外的信息，所以必须单独组织成一层。

### 68. 追问：雨后变湿题和河流题最本质的差别是什么？

**答：**

河流题核心是“水位历史和边界线”，雨后题核心是“全局降雨量、暴露度、材质吸水差异和局部积水潜力”。前者更像一个带方向和边界的事件，后者更像一个全场环境状态。

### 69. 追问：为什么你总说要做统一材质函数？

**答：**

因为如果每个材质各自去算湿润、积雪、污染，短期可能快，但长期完全不可维护。统一材质函数能统一输入、统一调试、统一升级，然后把差异留给响应参数。

### 70. 追问：那人工修正为什么还必须留？

**答：**

因为自动逻辑再强，也很难直接满足关卡镜头和特定构图需求。真实项目里一定会有 vertex color、decal、体积和 override 参数这种“把最后 20% 拉正”的手段。

### 71. 追问：如果面试官继续追“那数据具体放哪”，你怎么答得更像项目人？

**答：**

我会直接分层说：全局阶段值放 MPC 或管理器，区域边界和流向放 spline / volume，场景状态大范围写 RVT，局部动态交互写 RT，资产差异放材质实例参数或数据表，最后用 vertex color 和 decal 留人工修型口。

### 72. 追问：你最怕哪种数据组织方式？

**答：**

最怕“每个材质自己加一个参数、每个蓝图自己控制一套逻辑”。这种方案最开始看起来快，但过几个关卡之后就会不可维护，也很难统一升级。

### 73. 追问：如果题目里既有地表又有道具，你会先答哪个？

**答：**

我会先答统一驱动，再分别讲地表和道具怎么响应。这样顺序最稳，因为先把共享逻辑讲清楚，再讲差异，听起来会像系统方案。

### 74. 追问：如果面试官问“你为什么老不先讲材质节点”，你怎么回？

**答：**

我会说材质节点是最后一层，真正决定系统能不能成立的是驱动数据和组织方式。节点怎么搭只是实现细节，数据组织不对，节点搭得再漂亮也很容易碎。

### 75. 追问：这类实战题最能拉开差距的一句话是什么？

**答：**

我觉得是：`我会先把它说成一条数据链，再决定材质、粒子和后处理分别放在哪一层。` 这句会让你明显像在做项目，而不是只在想某个工具。

## 六、平台、性能与取舍追问

### 76. 追问：为什么你回答 `Nanite`、`Lumen` 这些题时，总先问平台和帧率？

**答：**

因为这些问题没有约束条件就没有真正的答案。同一个特性，在高端特例项目和广覆盖量产项目里的结论完全可能不一样。

### 77. 追问：为什么你会区分“支持口径”和“默认主线方案”？

**答：**

因为真实项目里，能跑和能当主线是两回事。一个特性即使在特定条件下有支持口径，也不代表它适合作为需要广覆盖、稳定上线的默认方案。

### 78. 追问：如果别人追问“那你到底是支持还是不支持”，你怎么答？

**答：**

我会说我不把它答成二元判断，而是先区分高配特例和广覆盖主线。真正成熟的结论不是一句 yes/no，而是“在哪些条件下可以、在什么范围内不该依赖它”。

### 79. 追问：为什么平台题里你总讲资源双轨？

**答：**

因为很多平台问题不是开关问题，而是资源组织问题。比如高配可以吃高精几何和高成本材质，但低配必须有 fallback mesh、简化材质和更便宜的光照方案，否则根本没法落地。

### 80. 追问：如果面试官问“高配、中配、低配你怎么定义”，你怎么答？

**答：**

我会说不是按感觉分，而是按平台和目标帧率做一张分级表。每一档都要明确：目标分辨率、目标帧率、允许的光照方案、阴影方案、材质复杂度和资源轨道。

### 81. 追问：为什么你说分级不是一个“全局质量值”？

**答：**

因为真正可上线的分级不是一个滑条，而是平台、特性、资源和运行时规则四张表。不同系统要能独立控制，不能什么都绑在一个值上一起糊降。

### 82. 追问：如果 GPU 爆了，你最先想看什么数据？

**答：**

我最先看 GPU 时间分布，也就是到底是 BasePass、阴影、透明、GI 还是后处理在吃预算。先做成本归因，后面才知道该砍哪个系统，而不是无差别全场降质量。

### 83. 追问：那 CPU 爆了你最先看什么？

**答：**

我会先看 Draw Call、Tick、物理、AI、CPU 粒子和动态生成销毁。这一类题如果还只盯着 shader，其实就说明没有先把瓶颈归因分清。

### 84. 追问：如果场景里透明很多，为什么你说这是像素问题？

**答：**

因为透明最容易爆的是 overdraw 和 fillrate，也就是一个像素被画了很多次。它不一定是几何量最大的问题，但往往是像素成本最可怕的问题。

### 85. 追问：如果面试官问“那你怎么保画质”，你会怎么说？

**答：**

我会先说不是所有东西都一起降，而是先守住最值钱的信息，比如主轮廓、主明暗关系和核心交互反馈。降级的本质不是全体变差，而是把高成本实现换成更便宜的载体，同时保留关键视觉信息。

### 86. 追问：为什么你说降平台时要先把“视觉目标”和“实现手段”分开？

**答：**

因为如果不分开，就会把某个具体特性误当成目标本身。比如我真正想保的是高质量空间感，不一定非要坚持某一种 GI 实现方式。

### 87. 追问：如果老板说“高端效果不能砍”，你怎么处理？

**答：**

我会尽量保住视觉结果，但不死守实现路径。也就是高配保原方案，中低配换 fallback，同时确保镜头和核心体验不崩。这比一刀全砍或者硬撑原方案都更像项目解。

### 88. 追问：为什么你总强调验证方案？

**答：**

因为性能题如果没有 profile、实机、温控和回归场景，所有回答都很像 PPT。真正上线的问题不在“方案听起来对不对”，而在“它在目标设备上稳不稳”。

### 89. 追问：如果只有两周时间做性能优化，你怎么排优先级？

**答：**

我会先抓最大的系统级瓶颈，再抓热点场景，再抓设备白名单和 fallback。时间很短时最忌讳平均发力，应该优先处理“最贵、最常见、最影响上线”的那一档问题。

### 90. 追问：平台题里最能体现成熟度的一句话是什么？

**答：**

我觉得是：`我会先问约束，再做分级，再落 fallback，最后用实机和回归验证。` 这句能一下子把你和“只会背特性支持表的人”区分开。

## 七、协作、复盘与表达追问

### 91. 追问：如果你和美术合作，这类系统你最重视什么？

**答：**

我最重视的是把自动逻辑和人工控制边界提前说清楚。自动逻辑保证大方向统一，人工控制负责镜头和局部修型，这样团队配合会顺很多。

### 92. 追问：如果你和程序合作，这个项目里最需要对齐的是什么？

**答：**

最需要对齐的是驱动数据和生命周期。比如哪些数据是全局状态、哪些是局部状态、谁来写、谁来读、什么时候失效，这些一旦对齐，后面很多实现细节都会顺很多。

### 93. 追问：如果别人不理解你为什么要花这么多时间做正确性，你怎么解释？

**答：**

因为很多效果在镜头里看起来成立，不代表它在系统里真的成立。把正确性补齐，后面才能稳定扩展，否则一到阴影、遮挡、平台和关卡复杂度上来就会崩。

### 94. 追问：你怎么判断一个方案是“demo 方案”还是“项目方案”？

**答：**

我通常看 4 件事：有没有统一数据组织、有没有多资产可复用性、有没有人工控制口、有没有 fallback 和验证方法。有这些才更像项目方案。

### 95. 追问：你怎么向面试官证明你不只是会写文档？

**答：**

我会把文档和真实结果绑在一起讲。比如先展示最终效果，再展示 `SceneDepth / ShadowDepth / VSM` 验证，再补文档只是为了说明我知道为什么这么做，而不是只会整理笔记。

### 96. 追问：如果面试官追问“你有没有带团队经验”，但你主要是自己做的，你怎么答？

**答：**

我不会硬说带团队，我会强调我对协作边界的理解，比如怎样给美术留 override、怎样把系统参数化、怎样用文档降低沟通成本。这也能体现协作能力，而且更诚实。

### 97. 追问：你做这个项目时，最像“工程决策”的一个瞬间是什么？

**答：**

我觉得是决定把 receiver 的 shadow invalidation 明确切到 `Always`。这不是一个炫技点，而是一个语义判断：当前系统确实是由外部 field 驱动阴影变化，那就该用符合语义的工程解。

### 98. 追问：你做这个项目时，最像“技术美术判断”的一个瞬间是什么？

**答：**

我觉得是意识到效果不该继续堆元素，而该先把边界、pulse、折射和内部层次的主次关系站稳。这个判断更像在做视觉结构，而不是单纯加特效。

### 99. 追问：如果你再做一个类似项目，你最想改进什么工作方式？

**答：**

我会更早把数据组织、验证路径和平台分级写成图，而不是只存在脑子里。这样不管是自己迭代还是和别人协作，都会更快进入对的问题空间。

### 100. 追问：最后一个问题，你希望面试官从这套项目里记住你什么？

**答：**

我希望他记住的不是“我做了一个蓝色裂隙”，而是“我能把一个效果从视觉概念接成一个真正被渲染系统承认的项目方案，而且能把它讲清楚、拆清楚、验证清楚”。

## 结尾建议

如果你真的要拿这篇练，最推荐的方式是：

1. 先练 `1-15`，把项目介绍练顺
2. 再练 `31-45`，把 shadow/VSM 练顺
3. 再练 `61-75` 和 `76-90`，把数据组织和平台题练顺
4. 最后练 `91-100`，把表达和协作抬起来

这 4 轮刷完，你面试时的稳定度会明显上一个台阶。
