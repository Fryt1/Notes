# 02 渲染管线与全链路复盘

> 这一篇的目标只有一个：  
> **把当前版本的 RealityDistortion 从 field / receiver 一路串到主视图挖洞、阴影、VSM、HoleInfo、Composite，以及编辑器转换工具，按现在真实生效的结构讲清楚。**

旧版本里最容易误导人的地方有两个：

- 把 `FDistortionSceneProxy` 讲成“强制动态路径”
- 把 `DrawStaticElements()` 置空讲成最终答案

这两个结论都已经过时。  
当前版本真正成立的，是：

**receiver 常规提交回到静态路径；RD pass 仍然按当帧 field 做动态粗筛；阴影侧通过条件式 invalidation 只让相交 receiver 重绘。**

---

## 一、先把这套系统拆成 6 条并行链

```text
A. Field 数据链
UDistortionFieldComponent
  -> FieldHandle
  -> Renderer RT Snapshot
  -> 各 pass 共享的 field 参数

B. Receiver 身份链
UDistortionMeshComponent / UDistortionInstancedMeshComponent
  -> CustomPrimitiveData[0]
  -> FDistortionSceneProxy / Instanced proxy
  -> 告诉各 pass “谁是 receiver”

C. 常规渲染 / 阴影提交链
FDistortionSceneProxy (基于 FStaticMeshSceneProxy)
  -> 静态 mesh command / 静态 shadow mesh
  -> DrawStaticElements()
  -> GetViewRelevance()

D. RealityDistortion 自定义 pass 链
SceneVisibility
  -> EMeshPass::RealityDistortion
  -> FRealityDistortionPassProcessor
  -> RealityDistortionShader.usf
  -> HoleInfoTexture

E. 深度 / 主视图 / 阴影 correctness 链
DepthOnly / BasePass / ShadowDepth / VSM
  -> shader clip
  -> shadow cache invalidation
  -> 最终受影结果一致

F. 内容准入与编辑器工具链
DistortionEditorConversion
  -> receiver 过滤
  -> 高风险资产跳过
  -> enable / disable selected receivers
```

一定要记住：

- **蓝色裂隙视觉** 不等于 **主视图几何真的挖掉**
- **主视图洞成立** 不等于 **阴影一定对**
- **阴影 correctness 对了** 也不等于 **性能一定合理**
- **shader 结果不对** 也不一定等于 **统一的 renderer 逻辑全错了**

---

## 二、Field 数据现在是怎么进 renderer 的

### 1. `UDistortionFieldComponent` 是统一 field 数据源

关键文件：

- `Source/RealityDistortion/Rendering/DistortionFieldComponent.h`
- `Source/RealityDistortion/Rendering/DistortionFieldComponent.cpp`
- `Engine/Source/Runtime/Renderer/Public/RealityDistortionField.h`
- `Engine/Source/Runtime/Renderer/Private/RealityDistortionField.cpp`

这一层负责的不是画效果，而是统一维护：

- `Center`
- `Radius`
- `Strength`
- `bEnabled`
- receiver 过滤相关语义

它通过 `FieldHandle` 把 GT 上的参数推到 RT，最后形成 renderer 可读的 field 快照。

### 2. 为什么这一层这么关键

因为后面依赖这份数据的，不止一个 shader，而是整条系统：

- `RealityDistortion` pass 的 field 粗筛
- `DepthOnly / BasePass / ShadowDepth` 里的 receiver 裁切
- VSM invalidation 判定
- `Composite` 的 dominant field 重建

如果这一层不统一，后面最糟糕的情况就是：

**每个 pass 都以为自己在处理同一个洞，实际上用的不是同一份 field 世界观。**

---

## 三、Receiver 现在是怎么被识别出来的

### 1. `UDistortionMeshComponent` 的职责

关键文件：

- `Source/RealityDistortion/Rendering/DistortionMeshComponent.cpp`

它当前做的事情是：

- `CreateSceneProxy()` 返回 `FDistortionSceneProxy`
- `SetCustomPrimitiveDataFloat(0, 1.0f)` 给 receiver 打标记
- receiver 启用时把 `ShadowCacheInvalidationBehavior` 设成 `Always`
- receiver 关闭时回到 `Auto`

这里一定要注意当前语义：

#### `Always` 现在只是“入场券”

它的意义不再是：

> “这个 primitive 永远每帧都要重绘阴影。”

而是：

> “这个 primitive 进入 VSM 那个每帧会检查 invalidation 的集合。”

真正是否需要 invalidation，由 proxy 的运行时判断决定。

### 2. instanced receiver 的身份链

关键文件：

- `Source/RealityDistortion/Rendering/DistortionInstancedMeshComponent.cpp`

这套 instanced receiver 仍然沿用同样的 receiver 标记语义：

- `CustomPrimitiveData[0]`
- receiver 开关
- `ShadowCacheInvalidationBehavior`

所以当前系统已经不是“只有 legacy 单 mesh receiver 才能进 RD 体系”，而是：

**只要 primitive 带对 receiver 语义标记，RD pass 和相关 shader 就能泛化识别。**

## 四、Receiver 的常规提交路径现在为什么是“静态主路径”

### 1. `FDistortionSceneProxy` 当前的真实职责

关键文件：

- `Source/RealityDistortion/Rendering/DistortionSceneProxy.h`
- `Source/RealityDistortion/Rendering/DistortionSceneProxy.cpp`

当前版本里，`FDistortionSceneProxy` 已经不再是旧文档里那种：

- 强制 `bDynamicRelevance = true`
- 主体依赖 `GetDynamicMeshElements()`
- `DrawStaticElements()` 置空

当前真实情况是：

- 它基于 `FStaticMeshSceneProxy`
- `GetViewRelevance()` 先沿用父类静态路径语义
- `DrawStaticElements()` 调父类，允许静态 shadow mesh 注册
- 只在需要时补充 receiver 自己的阴影与 RD 语义控制

### 2. 为什么回到静态路径能显著降低 draw call

因为旧问题不是“field 判定太慢”，而是：

- receiver 常规渲染和阴影长期走了更昂贵的动态提交思路
- 即使 invalidation 判定是对的，提交成本也已经先炸了

回到静态路径以后，UE 能重新利用：

- 静态 mesh command
- 静态 shadow mesh
- 更便宜的常规收集路径

这就是为什么那一轮性能拐点，不是靠继续调 VSM cvar 拿到的，而是靠：

**先把 receiver 从错误的提交结构里拉回来。**

### 3. 为什么 `DrawStaticElements()` 现在必须调父类

旧文档里“置空 `DrawStaticElements()`”曾经有阶段性意义，因为当时是在防止旧静态路径偷偷画回错误结果。

但现在的结构已经变了。

当前如果继续置空它，会直接损失：

- 静态 shadow mesh 注册
- VSM 对不相交 receiver 的缓存能力

所以当前正确做法是：

- `DrawStaticElements()` 调父类
- 相交 receiver 通过 invalidation 重绘
- 不相交 receiver 保留静态缓存收益

## 五、RealityDistortion Pass 现在是怎么工作的

### 1. pass 入口仍然是 `SceneVisibility -> EMeshPass::RealityDistortion`

关键文件：

- `Engine/Source/Runtime/Renderer/Private/SceneVisibility.cpp`
- `Source/RealityDistortion/Rendering/RealityDistortionPassProcessor.cpp`

`SceneVisibility` 负责把 primitive 挂进 `EMeshPass::RealityDistortion`。  
这件事的重要性在于：

**你的自定义 pass 先得成为 renderer 调度图的一部分，后面 shader 和 draw command 才有存在意义。**

### 2. `FRealityDistortionPassProcessor` 现在的 3 个关键动作

#### 第一层：receiver 识别

- legacy `FDistortionSceneProxy`
- 或者 `CustomPrimitiveData[0]` 打标的 instanced receiver

#### 第二层：field 空间粗筛

当前仍然按“当帧 field 快照”做包围球相交粗筛。  
这也是为什么当前 pass 仍然注册成：

- `EMeshPassFlags::MainView`

而不是：

- `CachedMeshCommands | MainView`

因为一旦允许缓存，receiver 提交集合就可能停留在旧的 field 位置对应结果。

#### 第三层：优先沿原始材质链提交

这一点是当前版本非常关键的新变化。

现在的顺序是：

1. 先沿 `MaterialRenderProxy -> Fallback` 链找可用 shader
2. 尽量使用原始材质链提交 RD pass
3. 只有材质没有为 RD pass 编译对应 shader 时，才退到默认材质

这一步的价值是：

**让 RD pass 和 BasePass 在两面性、WPO、PDO、裁剪逻辑上尽量一致。**

也正因为如此，黑块问题后面才能被明确地归因到“特殊 receiver 内容结构”，而不是“RD pass 本身完全错了”。

### 3. `HoleInfoTexture` 当前仍然主要记录什么

当前最关键的有效信息仍然是：

- `DeviceZ`

也就是说，RD pass 的本质仍然是：

**记录洞表面的屏幕空间深度信息，供后面的 fullscreen composite 做重建。**

## 六、主视图洞是在哪一层真正成立的

关键文件：

- `Engine/Source/Runtime/Renderer/Private/DepthRendering.cpp`
- `Engine/Shaders/Private/DepthOnlyPixelShader.usf`
- `Engine/Source/Runtime/Renderer/Private/BasePassRendering.cpp`
- `Engine/Shaders/Private/BasePassPixelShader.usf`

这一层的职责非常直接：

- `DepthOnly` 承认洞
- `BasePass` 承认洞

如果没有它们，`Composite` 再漂亮也只是屏幕上的假象。

### 运行时稳定性补丁为什么属于这一层

这次的 `DepthOnly` fatal 不是视觉问题，而是运行时资源绑定问题。

最终稳定做法集中在：

- `DepthRendering.h` 声明 `FRealityDistortionDepthPassUniformParameters`
- `FDepthOnlyPS::GetShaderBindings()` 主动绑定 `RealityDistortionDepthPass`
- `UniformBuffer_MultiFrame`
- 每帧更新 uniform buffer 内容

这说明这条链现在解决的已经不只是：

- 洞能不能成立

还包括：

- 预深度在真实运行时能不能稳定提交

## 七、阴影和 VSM 现在到底是怎么闭环的

### 1. `ShadowDepth` 负责让光源视角承认洞

关键文件：

- `Engine/Source/Runtime/Renderer/Private/ShadowDepthRendering.cpp`
- `Engine/Shaders/Private/ShadowDepthPixelShader.usf`

这一层负责的是：

- receiver 进入阴影收集路径
- field 内片元执行 `clip`
- 光源视角下的挡光关系被改写

### 2. 但 `ShadowDepth` 对了并不代表 VSM 一定对

因为后面还有：

- cache
- projection
- 最终 `ShadowFactor`

这正是这轮项目里最值钱的 renderer 认知之一。

### 3. 当前真正成立的是“条件式 invalidation”

关键项目文件：

- `Source/RealityDistortion/Rendering/DistortionSceneProxy.cpp`

关键引擎文件：

- `Engine/Source/Runtime/Engine/Public/PrimitiveSceneProxy.h`
- `Engine/Source/Runtime/Renderer/Private/ShadowScene.cpp`
- `Engine/Source/Runtime/Renderer/Private/VirtualShadowMaps/VirtualShadowMapCacheManager.cpp`

当前闭环是：

1. component 侧把 receiver 送进 `Always` 这条每帧检查的集合
2. 引擎侧支持运行时 override invalidation 行为
3. proxy 用 field 相交关系动态返回：
   - 相交：`Always`
   - 不相交：`Static`

这意味着：

- 相交 receiver 的阴影页会重绘
- 不相交 receiver 继续复用缓存

也就是：

**真正正确的说法已经不是“Always invalidating 是最终解”，而是“Always + 运行时 override = 条件式 invalidation”。**

---

## 八、Composite 现在解决的是什么，不解决什么

关键文件：

- `Engine/Source/Runtime/Renderer/Private/DeferredShadingRenderer.cpp`
- `Engine/Shaders/Private/RealityDistortionComposite.usf`

`Composite` 当前负责的是：

- 从 `HoleInfoTexture` 读洞表面深度
- 重建洞表面 world position
- 找 dominant field
- 做边界、pulse、折射、厚度、glow 等最终视觉

它不负责的是：

- 让前面的 opaque receiver 真正消失
- 让错误 receiver 自动变成“合适的 receiver”

### 这一层新增的调试能力

当前已经有几个很值钱的调试入口：

- `r.RealityDistortion.CompositeDebugMode`
- `r.RealityDistortion.CompositeNegativeDepthGapTolerance`

它们最大的价值不是“调风格”，而是：

**帮助你区分到底是 HoleInfo 没有写、dominant field 不对，还是 composite 采到的背景本来就不成立。**

---

## 九、为什么黑块问题最后会落到“内容准入”

这一条虽然在 [[14 黑块问题收束：Receiver 分类、高风险资产过滤与编辑器工具]] 里有更完整展开，但在全链路里也必须先记住一句：

**当前 receiver 语义默认假设：前层被裁掉以后，后面会是合理的背景。**

对普通墙体、柜体、建筑块面，这个假设通常成立。  
但对下面这些对象，它经常并不成立：

- 大型地面 / 路面 / 超大薄平面
- 伞面 / 棚布 / 遮阳结构
- 树叶 / 草 / 灌木 / 双面卡片植被
- 多层壳体和自遮挡很重的特殊结构

所以这轮最终新增的：

- 高风险过滤
- 标签覆盖
- 启停 receiver 工具

不是附属小功能，而是当前全链路里正式的一环。

---

## 十、当前最准确的全链路总结

如果把现在这套链路压成一句话，最准确的概括是：

> `UDistortionFieldComponent` 维护统一 field 数据；  
> receiver 通过 `CustomPrimitiveData[0]` 和自定义 proxy 进入系统；  
> 常规渲染与阴影回到静态提交路径；  
> RD pass 仍按当帧 field 粗筛并优先沿原始材质链写 `HoleInfoTexture`；  
> `DepthOnly / BasePass / ShadowDepth / VSM` 共同承认这个洞；  
> VSM 通过“Always 入场 + 运行时 override”实现条件式 invalidation；  
> 黑块问题则通过 receiver 资产过滤和编辑器工具进入内容层闭环。

---

## 结论

当前版本最重要的变化，不是又加了一个新 shader，而是整条渲染链的职责边界终于清楚了：

- 谁负责 field
- 谁负责 receiver 身份
- 谁负责常规提交
- 谁负责 RD pass
- 谁负责 correctness
- 谁负责内容准入

当这些边界清楚之后，性能问题、黑块问题、VSM 问题才终于开始从“混在一起的大问题”变成可以分层处理的小问题。
