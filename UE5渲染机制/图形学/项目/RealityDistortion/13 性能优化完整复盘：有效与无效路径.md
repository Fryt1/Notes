# 13 性能优化完整复盘：有效与无效路径

> 这一篇不是简单记录“最后改了哪几个参数”，而是把这次性能优化里每一条**有效路径**和**无效路径**都拆开讲清楚。
> 真正值钱的不是某一个 cvar，而是：
> **如何把一个看起来很乱的 UE5 渲染卡顿，拆成可验证、可排除、可收敛的问题树。**

---

## 一、问题最初长什么样

最开始的症状是：

- 开启 receiver shadow 之后帧时间直接爆炸
- 直觉上怀疑是 `VSM` 或者 receiver 的阴影更新方式有问题
- 场景里 receiver 数量很多，量级接近 `1000`
- `RealityDistortion` 效果本身在主视图是对的，但整帧非常卡

后面逐步确认：

- `Distortion` 自己的 GPU 成本其实很小，后期稳定下来大约只有 `~1 ms`
- 真正的瓶颈先后出现在：
  - receiver 阴影提交流程
  - VSM / shadow 相关 GPU 开销
  - 更后面的 `DeferredLighting / TSR / PostProcessing / Lumen`
  - 编辑器视口额外开销

这意味着：  
**问题不是“某一个 shader 写炸了”，而是渲染路径、缓存策略、线程等待和 UE5 默认特性的组合问题。**

---

## 二、第一步为什么是“先切层”，而不是立刻改代码

这次最重要的第一步，不是直接改 shader，也不是直接调画质，而是先回答：

1. 卡的是不是 `RealityDistortion` 自己？
2. 卡的是不是 receiver 的 shadow 路径？
3. 卡的是 CPU 逻辑、渲染线程，还是 GPU？
4. profiler 里显示高的那个桶，到底是根因，还是“在等别的东西”？

这一步最值钱的地方在于：  
如果一开始切层切错，后面会一直在错误方向上做“局部正确、整体错误”的优化。

---

## 三、第一批有效路径：为什么这些操作有价值

## 3.1 `r.RealityDistortion.DisableReceiverShadow 1`

### 操作

先直接关掉 receiver shadow，看卡顿是否大幅缓解。

### 为什么有效

这一步不是为了长期方案，而是为了做**最快速的问题切分**。

如果一关 receiver shadow，性能立刻明显恢复，就说明：

- 问题主要不在主视图的 RD pass
- 主要不在材质本身
- 问题集中在 receiver 参与的 shadow / VSM / lighting 路径

### 这一步带来的结论

这次排查里，这一步非常关键。因为它把问题从“整个项目都可能有问题”，直接收缩成了：

- receiver 是否错误地进入了昂贵的 shadow 提交流程
- VSM 是否对这些 receiver 做了过重的缓存失效或重绘

换句话说，这一步虽然没有“修问题”，但它把问题从大海缩成了水桶。

---

## 3.2 看 `stat unit / stat gpu / ProfileGPU`

### 操作

不是只看总帧时间，而是反复交叉看：

- `stat unit`
- `stat gpu`
- `ProfileGPU`
- `stat initviews`
- `stat game`

### 为什么有效

因为这几张表负责回答的是不同层次的问题：

- `stat unit` 看整帧是偏 GT、RT、RHIT 还是 GPU
- `stat gpu` 看 GPU 哪个大桶最贵
- `ProfileGPU` 把大桶再拆成具体 pass
- `stat initviews` 看可见性 / 剔除到底是不是主线
- `stat game` 看 GT 里到底有没有真实逻辑工作

### 这一步带来的关键认知

这轮排查里，最重要的几个结论几乎都来自 profiler：

- `Distortion` 本身并不贵
- 很多时候 `HZB / occlusion` 高，不代表它自己算得慢
- `Game` 高，不一定是逻辑真重，可能是在等
- `Postprocessing` 高，也不代表 Bloom / DOF 真高，必须继续展开

---

## 3.3 receiver 回归静态路径：这是决定性的一刀

### 之前为什么会卡

receiver 虽然从效果上看没有改 mesh 拓扑，只是在 shader 里做 clip，但它之前并没有真正吃到静态提交路径的好处。

之前的结构问题本质上是：

- receiver 被强制当成更偏动态的提交方式去处理
- 每帧手工提交 mesh / shadow
- 结果是 draw call、shadow 收集和 CPU 提交流程一起放大

### 这次有效的改法

这次真正打中问题的一刀是：

- `DistortionMeshComponent` 不再强制 `Movable`
- receiver 回归静态 mobility
- `DistortionSceneProxy` 不再默认走那条昂贵的动态提交主路径
- 常规渲染和阴影尽量走静态 mesh command / 静态 shadow mesh 路径

对应项目里的关键文件是：

- `Source/RealityDistortion/Rendering/DistortionMeshComponent.cpp`
- `Source/RealityDistortion/Rendering/DistortionSceneProxy.cpp`

### 为什么这一刀有效

因为它解决的是**结构性浪费**，不是数值调优。

它直接减少了：

- receiver 的无意义动态提交
- 每帧手工组装批次的成本
- shadow 提交流程里的 CPU 放大

### 实测意义

这一刀做完后，receiver 相关 draw call 明显下降。

当时最重要的量级变化是：

- 之前开启 receiver shadow，draw call 一度到 `8000+`
- 改回静态路径后，开启 receiver shadow 下降到大约 `2700+`
- 再临时关掉 receiver shadow 时，基线大约在 `1100`

这说明最夸张的那一段爆炸，主要就是错误的提交路径造成的。

---

## 3.4 “相交才重绘，不相交走缓存”的思路本身是对的

### 核心想法

receiver 本身不移动，真正变化的是：

- 力场和 receiver 相交时，阴影形状会被 clip
- 不相交时，阴影形状其实是稳定的

所以正确方向一定是：

- 不相交：尽量走缓存
- 相交：再做重绘或 invalidation

### 为什么这条思路有价值

这不是某一个实现技巧，而是整个阴影优化的正确目标函数。  
它定义了后面所有 VSM 调整的方向：

- 不是“所有 receiver 都每帧 Always”
- 也不是“为了省性能直接不投影”
- 而是“只把变化的那部分成本留给变化的 receiver”

### 结论

这条思路是对的。  
后面很多实验即便没有直接成为最终方案，本质上也都是围绕这个目标在找可行实现。

---

## 3.5 为什么改回静态路径后，`conditional invalidation` 才真正变成了性能收益

### 先把三个概念拆开

这里最容易混淆的是三件事：

- `invalidation`：旧的 VSM cache page 要不要作废、要不要重绘
- `submission path`：这个 primitive 这一帧到底走静态提交，还是走动态收集 / 动态提交
- `draw call / visibility` 成本：这一帧 CPU 到底要不要重新收集它、剔除它、组装它、向多个 view 提交它

这三件事不是同一层的东西。

`invalidation` 只回答第一个问题：  
“旧页要不要失效？”

它**不回答**下面这两个问题：

- “这个物体这一帧还要不要走动态收集？”
- “这一帧还要不要重新参与 shadow view 的提交和可见性任务？”

### 为什么之前 `dynamic path + conditional invalidation` 还是很贵

之前的 receiver 虽然从效果上看没有改 mesh 拓扑，只是在 shader 里做 clip，但提交路径上并没有真正吃到静态缓存。

当时更接近的是这种状态：

- receiver 还在走动态相关路径
- 每帧还要重新收集 mesh
- 每帧还要重新参与 shadow 相关 view 的提交
- 每帧还要吃 `LaunchVisibilityTasks / VisibilityCommands / Draw` 这一整套 CPU 成本

所以就算 `GetShadowCacheInvalidationBehavior()` 已经开始返回：

- 相交时 `Always`
- 不相交时 `Static`

它省掉的也只是“VSM 页是否需要重绘”的那一层成本。  
但动态路径本身的提交、收集、可见性、shadow view 参与成本，还是继续在付。

这就是为什么当时会出现一种很容易误解的现象：

- 逻辑上已经不是“全量重绘”
- 但 draw call、VisibilityCommands、渲染线程耗时仍然很高

不是因为思路错了，而是因为优化只落在了 `invalidation` 层，没有落到 `submission path` 这一层。

### 不重绘，不等于这一帧没有成本

这点一定要单独记住：

> “这个 receiver 本帧没有触发 VSM 重绘”
> 不等于
> “这个 receiver 本帧没有参与任何提交成本”

如果它还走动态路径，那么即使最终没有真的去重绘 shadow page，它也可能仍然在消耗：

- 动态 mesh 收集
- 可见性任务
- shadow view 下的 primitive 处理
- mesh batch 组装
- draw command 提交相关 CPU 时间

所以 `invalidation` 不满足时，省掉的是“重绘页”这笔钱；  
但如果路径还是动态的，别的 CPU 账单照样在付。

### 为什么改回静态路径后，收益一下子落地了

真正决定性的变化不是“又调了一个 VSM 选项”，而是 receiver 回到了静态提交思路：

- `DistortionMeshComponent` 不再强制 `Movable`
- `DistortionSceneProxy` 不再默认走那条昂贵的动态收集主路径
- 常规渲染和阴影尽量回到静态 mesh command / 静态 shadow mesh 的缓存路径

这样以后：

- 不相交的 receiver：既不需要 invalidation，也更容易真正复用静态缓存
- 相交的 receiver：才进入 `Always`，让 VSM 去重绘变化的页

这时 `conditional invalidation` 才和静态缓存路径真正配套起来。  
也就是：

- 静态路径负责“让不变的东西别反复提交”
- conditional invalidation 负责“让变化的东西只重绘必要部分”

两者缺一不可。

### 为什么这会直接反映到 draw call 上

这里降低 draw call，不是因为“自动实例化”了，也不是因为 mesh 数量突然变少了。  
真正减少的是：

- 每帧重复动态提交的次数
- shadow 相关 view 里重复收集 / 重提的次数
- 本来不该每帧重新走的那部分 CPU 提交流程

所以它表现出来就是：

- 开 receiver shadow 时，早期一度到 `8000+`
- 回到静态路径之后，降到大约 `2700+`
- 再关闭 receiver shadow 时，基线大约 `1100`

这说明之前最夸张的膨胀，并不只是“阴影本身贵”，更是“阴影叠加动态路径的错误提交方式”一起把成本放大了。

### 一句话总结

`conditional invalidation` 只负责决定“哪些页该重绘”；  
静态路径负责决定“哪些东西不要每帧重新提交”。

所以真正有效的组合不是：

- `dynamic path + conditional invalidation`

而是：

- `static path + conditional invalidation`

前者思路对，但收益落不实；  
后者才是这次性能真正开始明显改善的原因。

## 四、第一批无效路径：为什么这些方向最后被证明不对

## 4.1 全量 `Always` invalidation：方向对了一半，但太粗暴

### 当时为什么会想到它

因为 VSM 的缓存机制和阴影 clip 是天然冲突的：

- 缓存想复用旧页
- clip 想在力场移动时改阴影形状

所以最直观的办法就是让 receiver 走 `Always`。

### 为什么最后无效

因为 receiver 数量太多。  
如果接近 `1000` 个 receiver 全都 `Always`，GPU 等于每帧为大量 shadow caster 重绘 VSM 页。

结果是：

- `Shadow Depths`
- `RenderVirtualShadowMaps`
- shadow 相关 draw call

一起爆炸。

### 结论

“要 invalidation” 这个方向是对的；  
“所有 receiver 一起 Always” 这个实现是错的。

---

## 4.2 `MarkRenderTransformDirty()`：看起来像轻量通知，实际上很重

### 当时为什么会想到它

直觉上会觉得：  
“既然只想让阴影更新一下，那给 primitive 标一个 transform dirty 不就行了？”

### 为什么最后无效

因为 `MarkRenderTransformDirty()` 不只是设个 flag。  
它会把 primitive 送进一整套 scene info 更新流程，包括：

- bounds 更新
- scene octree / BVH 更新
- 相关 scene info 刷新

结果 profiler 里直接体现成：

- `UpdateAllPrimitiveSceneInfos` 很高

而且这条路径会把问题从“阴影缓存更新”变成“场景信息整体刷新”，CPU 侧非常亏。

### 结论

这条路最大的教训是：

> 不能把“通知阴影系统更新”错误地实现成“把整个 primitive 场景状态再过一遍”。

也就是：

- 目标很小
- 走的路太重

---

## 4.3 “不相交的 receiver 直接不投影”性能很好，但视觉不对

### 当时为什么会想到它

因为它是最直接砍 shadow draw call 的办法。  
只要不相交的 receiver 不提供 shadow mesh，VSM 就完全不用管它们。

### 为什么最后无效

因为你的场景里原始静态网格已经被 receiver 替换掉了。  
这意味着：

- receiver 不投影
- 就等于那块物体真的没有阴影了

所以虽然这条路一度把性能压得很好，甚至到过更舒服的帧时间区间，但视觉结果不成立。

### 结论

这是一次非常典型的“性能很好，但问题定义已经变了”的实验。  
它证明了一个重要边界：

> 这次优化不能靠“偷删阴影”完成，只能靠“让阴影变便宜”完成。

---

## 4.4 继续死盯 `Visibility / HZB`：中途一度像根因，后面证明不是主线

### 当时为什么会误判

中间有一段 profiler 里：

- `LaunchVisibilityTasks`
- `VisibilityCommands`
- `MapOcclusionResults`
- `RHICmdList_FlushRHIThread`

都很高，很容易让人以为：

> “是不是可见性剔除本身太慢？”

### 为什么后来证明不是主线

后面继续拆以后发现：

- `HZB` 自己的 GPU pass 其实很小，稳定后大约只有 `0.12 ms`
- `stat initviews` 里真正的：
  - `Compute View Relevance`
  - `View Visibility`
  - `Init dynamic shadows`
  都已经不高

更关键的是，引擎源码里 `FHZBOcclusionTester::MapResults()` 的 readback 会阻塞等结果：

- `Renderer/Private/SceneOcclusion.cpp`

这说明很多时候你看到的是：

- CPU 走到同步点
- 正在等 GPU 上一帧或前面那串 pass 把结果做完

而不是“HZB 自己算了几十毫秒”。

### 结论

`Visibility / HZB` 在这次问题里更像：

- 一个症状放大器
- 一个同步点
- 一个 GPU 队列过长后的表征

但它不是后期真正的主战场。

---

## 4.5 ISM / HISM：这次没有成为主解

### 当时为什么会尝试

因为理论上它可以：

- 减少 primitive 数量
- 降低 draw call
- 改善可见性开销

看起来很像“大量重复 receiver”的标准解法。

### 为什么这次没有预期收益

实际测试之后发现：

- mesh / material 组合本身就比较碎
- 即使做了 bucket，桶数量仍然不少
- 阴影提交并不是“一个 bucket 只画一次”，而是还会被：
  - component
  - section
  - shadow view
  再继续放大

实际日志里能看到：

- 源 actor 数量下降了
- 但 draw call 没有按预期等比例下降
- 有些情况下甚至还会变高

### 结论

这不代表 ISM/HISM 理论错了，而是说明：

> 在当前内容结构下，它不是第一 ROI。

也就是：

- 不是不能做
- 但不是这次先救性能的主刀

---

## 五、后半段为什么从“RD 系统优化”转成了“标准 UE5 GPU 预算优化”

当 receiver 的提交路径修正以后，问题开始发生阶段性变化。

后面 GPU profile 里最重的开始变成：

- `DeferredLighting`
- `ShadowDepths`
- `TemporalSuperResolution`
- `PostProcessing`
- `LumenScreenProbeGather`

这时候就说明：

- RD 的结构性问题已经不再是唯一主犯
- 剩下的是标准的 UE5 高级特性预算问题

也就是说，优化目标从：

- “修错的渲染路径”

转成了：

- “控制 UE5 默认图形栈的整帧预算”

## 六、后半段哪些调法有效，哪些没用

## 6.1 有效：关掉一部分灯的阴影

### 为什么有效

它直接减少了：

- shadow view
- shadow draw call
- lighting 阶段的开销

### 但为什么收益有限

因为到后面阶段，问题已经不是某几个坏灯单独导致，而是：

- shadow
- lighting
- TSR
- 后处理
- 编辑器视口合成

几块中等成本一起叠加。

### 结论

这条路有收益，但属于“减压”，不是“重构问题”的主解。

---

## 6.2 有效：`r.AntiAliasingMethod 2`

### 为什么有效

把 `TSR` 切成 `TAA` 后性能明显改善，说明：

- `TSR` 的确是后期一个真实大头

### 但为什么没成为最终方案

因为目标不是简单关掉 TSR，而是想保留 TSR 的画面表现。

### 结论

这一步的价值不在最终采用，而在于：

> 它用一次 A/B，证明了 `TSR` 确实值得继续优化。

---

## 6.3 无效：继续抠 Bloom / DOF / LensFlare / LocalExposure

### 为什么一开始会怀疑它们

因为 `stat gpu` 里看到 `Postprocessing` 高，很容易直觉上去关传统后处理项。

### 为什么最后证明没打中

后面把 `ProfileGPU` 里的 `PostProcessing` 展开以后，真实结构是：

- `TemporalSuperResolution` 才是最大子项，约 `3.03 ms`
- `LocalExposure` 很小，约 `0.04 ms`
- `Bloom` 很小，约 `0.07 ms`
- `Tonemap` 也不大，约 `0.26 ms`

也就是说：

- `Postprocessing` 这个桶高
- 不等于普通后处理高

### 结论

如果只看桶名、不展开 pass，就很容易在错误的地方浪费时间。

---

## 6.4 有效：把 `PostProcessing` 展开，而不是继续猜

### 这一步为什么重要

`showflag.PostProcessing 0` 的价值，是先证明：

- 后处理链整体确实是大头之一

但真正的突破来自下一步：

- 不停在桶级别
- 继续展开 `ProfileGPU`

最终确认：

- `TSR`
- `InitializeEditorPrimitivesTextures`
- `CompositeEditorPrimitives`
- `EditorSelectionOutlines`

这些才是后处理大头。

### 结论

这一步把“后处理很高”进一步翻译成了：

> “真正高的是 TSR 和编辑器视口合成，不是 Bloom、DOF 这种常规后处理项。”

---

## 七、为什么编辑器里测出来的结果不能直接当成最终游戏成本

后面 `ProfileGPU` 里明确能看到：

- `InitializeEditorPrimitivesTextures`
- `CompositeEditorPrimitives`
- `EditorSelectionOutlines`
- `Slate UI`
- `Editor Primitives`

这些都是编辑器视口本身的额外成本。

这意味着在编辑器里：

- 看到的 `PostProcessing`
- 看到的 `Draw`
- 看到的部分 GPU pass

都混进了编辑器噪音。

所以后面分析里，必须始终记住：

> 编辑器 profile 只能用于定位方向，不能直接等价成最终 runtime 成本。

---

## 八、这次最关键的几组阶段性结论

## 8.1 前期最重要的结论

- 问题最初确实和 receiver shadow / VSM 高度相关
- 错误的 receiver 提交流程，是最早那一波爆炸的关键原因

## 8.2 中期最重要的结论

- `MarkRenderTransformDirty()` 这条路不适合干 shadow invalidation
- “不相交就不投影”虽然快，但视觉定义错误
- ISM/HISM 在当前内容结构下不是第一收益点

## 8.3 后期最重要的结论

- `HZB / Visibility` 在后来已经不是主线

## 十、这次最值钱的方法论

这次真正值得记住的，不是某个具体 cvar，而是下面这套顺序：

1. 先切系统，不先猜具体原因  
2. 先确认是不是自己效果 pass 的锅  
3. 先修结构性错误，再调参数  
4. profiler 只看到桶不够，必须继续展开 pass  
5. 看到 `HZB / Wait / Flush` 高，要先问是不是在等 GPU  
6. 编辑器 profile 只能定位方向，不能直接当 runtime 真值  
7. 所有“优化很成功”的方案，都必须再问一次：效果定义有没有被偷改

这套顺序，是这次排障里真正能复用到以后任何复杂渲染问题上的部分。

## 十二、ISM 和 HISM：它们分别在解决什么问题

### 12.1 先一句话说清楚

- `ISM`：主要解决“同一种 mesh 重复很多次时，CPU 提交太多次”的问题
- `HISM`：在 ISM 的基础上，再解决“实例很多而且分布很广时，整组剔除太粗”的问题

所以：

- `ISM` 更偏向 **减少重复提交**
- `HISM` 更偏向 **减少大范围实例的可见性和 LOD 成本**

---

### 12.2 它们的共同前提

不管是 `ISM` 还是 `HISM`，都不是“把任何物体随便合起来画”。

它们都有一个硬前提：

- 同一个 component 里，本质上只能表示 **同一套 StaticMesh**
- 材质布局也必须兼容同一套 section 结构

所以它们天然就不是“跨 mesh 的大一统合批器”。  
如果场景里 mesh / material 本来就很碎，那么实例化的理论下限就不会特别低。

这也是为什么你日志里已经看到：

- `UniqueMeshes=165`
- `UniqueMeshMaterialSets=197`

这意味着即使完全不考虑空间拆分，只按 mesh/material 合并，桶数下限本身也已经不小了。

---

### 12.3 ISM 的原理是什么

`ISM = Instanced Static Mesh Component`

它做的事可以理解成：

- 只保留一份 mesh 资源
- 只保留一套材质/section 提交流程
- 但给 GPU 一整批 instance transform
- 让 GPU 在同一个 draw 里把这批实例画出来

也就是说，原来可能是：

- 100 个相同箱子
- 100 次“提交这个 mesh”

改成 ISM 以后更接近：

- 1 次“提交这个 mesh”
- 外加 100 份实例变换数据

所以 ISM 真正减少的是：

- CPU 侧重复提交
- 重复构建 mesh draw command 的次数
- 大量相同 primitive 的管理成本

它不是减少三角形，也不是减少像素。  
它减少的是“同样的东西不要一遍一遍从 CPU 往渲染器里塞”。

---

### 12.4 为什么 ISM 不一定让 drawcall 掉很多

这是最容易误会的点。

很多人会把 ISM 理解成：

> “100 个实例就一定从 100 个 draw 变成 1 个 draw”

实际上不是这么简单。  
真正更接近的关系是：

`Draw ≈ 组件数 × section 数 × pass 数 × view 数`

这里最关键的是后面三项：

- `section`
- `pass`
- `view`

#### `section`

一个 mesh 如果有 3 个材质 section，那么它不是 1 个 draw，而是至少按 section 拆成多次提交。

#### `pass`

同一个物体不只画 BasePass。  
还可能会画：

- Depth
- ShadowDepth
- 自定义 pass
- 其他附加 pass

#### `view`

开阴影以后，尤其是方向光阴影 / VSM / 多灯光时，并不是只有主相机这一个 view。  
每多一个 shadow view，本质上都可能再来一轮提交。

所以 ISM 减掉的主要是“实例数这一维”，但：

- section 不会自动消失
- 阴影 pass 不会自动消失
- 多 view 不会自动消失

因此它的效果更像是把：

`实例数 × section × pass × view`

压成：

`桶数 × section × pass × view`

如果：

- 你的桶数还是不少
- mesh/material 很碎
- 阴影和灯很多

那 drawcall 下降就不会像直觉里那么夸张。

---

### 12.5 HISM 比 ISM 多做了什么

`HISM = Hierarchical Instanced Static Mesh Component`

它不是另一种“更强的合批器”，而是在 ISM 之上再加了一层 **层次树**。

你可以把它理解成：

- `ISM`：一大包实例放在一起
- `HISM`：先把这一大包实例按空间做成树状节点

树里的每个节点都维护一个 bounds。  
当相机或 shadow view 做可见性判断时：

- 如果整个节点都不可能可见，就整节点跳过
- 只有节点可能可见时，才继续往下看更细的实例组

这就是 HISM 的核心价值：

- 不是先想着“少几个 draw”
- 而是先想着“别让一整个大包实例都被迫参与可见性和 LOD”

所以 HISM 更适合：

- 实例数量非常多
- 空间分布非常大
- 相机通常只会看到其中一小部分

典型就是：

- 植被
- 森林
- 路边重复道具
- 大世界散布型静态装饰

---

### 12.6 HISM 为什么常常更有利于 `VisibilityCommands`

因为 `VisibilityCommands / LaunchVisibilityTasks / ProcessVisibilityTasks` 这些成本，本质上都和“我要检查多少东西可见”有关。

如果只有 ISM：

- 一个 component 往往还是一个比较粗的整体
- 只要 bounds 还在视野附近，这整包实例就可能继续参与后续流程

如果是 HISM：

- 上层节点就可以先挡掉一大块实例
- 没必要把整包全拖进来

所以 HISM 的主要收益，经常不是：

- drawcall 立刻从 3000 变 300

而是：

- `VisibilityCommands`
- `LaunchVisibilityTasks`
- `ProcessVisibilityTasks`

这类“可见性 / 剔除调度成本”更容易下降。

---

### 12.7 为什么你这里实例化后，drawcall 可能没怎么掉，甚至变高

这不是反常，反而很符合你这个场景的结构。

原因通常是几件事叠在一起：

- 你的 mesh/material 本来就很碎，桶数下限不低
- 阴影 view 很多，draw 不是只按主相机算
- 每个桶仍然要按 section 提交
- 某些实例桶的 bounds 变大后，反而更容易被 shadow view 认为“需要处理”

所以你虽然把：

- `1762` 个对象

压成了：

- `304` 个桶

但 drawcall 没有线性跟着掉，这是正常的。  
因为 drawcall 从来就不是只由“对象个数”决定的，而是由：

- 桶数
- section 数
- 灯光 / shadow view 数
- pass 数

共同决定的。

换句话说：

> “对象数减少了”
> 不等于
> “drawcall 就按同样比例减少”

---

### 12.8 你当前项目里，更接近哪一种

你这次真正做进去的是 **ISM 路线**，不是 HISM。

也就是说，你现在做的是：

- 按 `mesh + material + 空间 cell + 状态` 先手工分桶
- 每个桶生成一个 `InstancedStaticMeshComponent`

这属于：

- **手工空间分桶 + ISM**

而不是：

- 一个超大 `HISM` 让引擎自己在内部做层次树剔除

所以你这次实验验证到的，更主要是：

- “当前内容结构下，实例化不是第一收益点”

而不是：

- “HISM 一定没有价值”

它们不是同一个结论。

---

### 12.9 实战里该怎么选

#### 用 `ISM` 的情况

- 同 mesh 重复很多
- 实例比较集中
- 主要矛盾是 CPU 重复提交
- 你更想减少 component / primitive 数量

#### 用 `HISM` 的情况

- 同 mesh 重复很多
- 空间分布很广
- 主要矛盾是可见性 / 剔除 / LOD
- 相机通常只能看到其中一部分

#### 两者都帮不大的情况

- mesh/material 非常碎
- 每种重复数量都不高
- 真正的大头是灯光、阴影 view、TSR、Lumen、后处理

这时就算做了实例化，也可能只能得到很有限的收益。

---

### 12.10 一句话结论

`ISM` 解决的是“同样的东西别重复提交”；  
`HISM` 解决的是“同样的东西分布很广时，别整包一起做可见性和 LOD”。

所以：

- 如果你卡在 `draw / CPU 提交`，先想 `ISM`
- 如果你卡在 `VisibilityCommands / 可见性调度`，再重点考虑 `HISM`

但无论哪一种，它们都不是“无条件降低一切成本”的万能键。  
最终收益大小，永远取决于：

- 内容是否重复
- mesh/material 是否碎
- 阴影和灯光 view 有多少
- 空间分布是否真的适合分层剔除
